# Hybrid Sparse Vector Storage on PDF Upload — Design

**Date:** 2026-08-16
**Scope:** `backend/app/rag/` upload pipeline only (`chunker.py`, `vector_store.py`, + one new module). The query workflow (`retriever.py`, `reranker.py`, `Hybrid_retrieval.py`) is explicitly out of scope for this change — this spec only gets storage ready for it.

## 1. Goal

Today `realtime_pdf_collection` stores only a dense embedding per chunk. To support a future hybrid-search query workflow (anchor chunk found via dense+sparse fusion, then context assembled around it), every chunk must additionally carry:

1. A **sparse (BM25) vector**, stored consistently alongside the dense vector.
2. A **document-global `chunk_seq`**, so the future query workflow can locate a chunk's neighbors (`chunk_seq ± N`) regardless of page boundaries, independent of the existing page-local `chunk_index`.

## 2. Mechanism: Milvus-native BM25 Function

Sparse vectors are generated by Milvus's built-in BM25 `Function` (pymilvus 2.6.3, already pinned in `backend/requirements.txt`), **not** the client-side `pymilvus.model.sparse.BM25EmbeddingFunction` used by the reference `Chunks.py` / `BM25_sparse_retrieval.py` in `backend/app/orchestrator/`.

That reference approach calls `bm25_ef.fit(texts)` once over whatever corpus exists at that moment, freezing IDF statistics; documents added afterward get sparse vectors but are scored against stale, day-one corpus statistics. It also requires the whole corpus to `fit()` up front, which doesn't fit an incrementally-growing realtime collection.

The native BM25 Function instead:
- Computes each row's sparse vector from its `text` field automatically, server-side, at insert time — no corpus fit step.
- Stores only raw term frequency per row. Corpus-level statistics (IDF, average doc length) are maintained by the collection itself and applied at **query** time, recomputed from whatever is currently indexed. Uploading a 2nd/3rd/Nth PDF automatically shifts scoring for all future queries — no re-fit, no staleness.
- Is schema-bound: `sparse_vector` is a Function *output* field, computed atomically as part of the same `insert()` call that writes `text`/`embedding`. There is no code path where dense succeeds and sparse fails independently for a given row — consistency is structural, not something the app has to enforce.

## 3. Analyzer choice: plain `"standard"`, not multi-language

Milvus supports a multi-language analyzer (`multi_analyzer_params` + a `language` field, picking e.g. an English or German stemmer per row). Decided **against** using it now:

- The actual cross-lingual scenario in this project (query in Chinese against an English/German doc, etc.) is not solvable by analyzer choice at all — BM25 is lexical term-matching; a Chinese query and an English document share no tokens under *any* analyzer. Cross-lingual retrieval is carried by the dense side (`EMBEDDING_MODEL = paraphrase-multilingual-MiniLM-L12-v2`, a multilingual embedding model), which is unaffected by this change.
- Multi-language analyzer only improves *same-language* recall (e.g. stemming "terminate" → matches "termination"), which is a real but marginal, laterable retrieval-quality tuning task — properly part of the query-workflow scope this spec explicitly excludes.
- Adopting it now would add a `language` field, a per-PDF language-detection step, and a new dependency, none of which are needed for storage correctness or consistency.

`"standard"` (Unicode tokenizer + lowercase, no stemming) is a safe, reversible default: same-language BM25 matching still works (exact/near-exact token overlap), it just doesn't stem. Revisiting this later means one more collection recreation — acceptable, since this project is at the dev/prototype stage and collection recreation has already been done once during this change.

Future note (not actioned here): if actual Chinese-language PDFs are ever uploaded (not just Chinese queries), `"standard"` under-segments CJK text (no whitespace boundaries) and would need the ICU tokenizer or a Chinese-specific analyzer at that point. Not a concern today — current corpus is EN/DE only (`sample_docs/`).

## 4. Schema change

`realtime_pdf_collection` was already dropped by the user (only contained one test PDF), so this is a clean create, not a migration. `get_collection()` will build the new schema on first call.

New schema (`id`, `text`, `embedding` unchanged in type; `sparse_vector` and the BM25 Function are additions):

- `id`: INT64, primary, auto_id (unchanged)
- `text`: VARCHAR(65535), **now with `enable_analyzer=True`** (required for BM25 Function; previously had no analyzer config since it wasn't tokenized for search)
- `embedding`: FLOAT_VECTOR(dim) (unchanged)
- `sparse_vector`: SPARSE_FLOAT_VECTOR — **new**, Function output field, never written to directly
- `Function(name="text_bm25_emb", type=BM25, input=["text"], output=["sparse_vector"])` — **new**
- Dynamic fields (`document_name`, `file_hash`, `page`, `chunk_index`, and new `chunk_seq`) — unchanged mechanism (`enable_dynamic_field=True`)

Index params:
- `embedding`: AUTOINDEX / COSINE (unchanged)
- `sparse_vector`: AUTOINDEX / BM25 (new)

### Failure mode: unsupported Milvus server

The BM25 Function requires Milvus ≥2.5. If the connected server is older, `create_collection()`/`create_index()` raises. This is **not** caught — it propagates unchanged up through `add_chunks()` → `upload.py`'s existing outer `try/except` → HTTP 400. No dense-only fallback. A fallback would silently recreate the exact inconsistency (some docs with sparse vectors, some without) this change exists to prevent, so failing loudly and requiring a server upgrade is the correct behavior.

## 5. Components

### New file: `backend/app/rag/hybrid_schema.py`

Pure, connection-agnostic schema/index builders — isolated from `vector_store.py`'s connection-caching logic so the schema definition can be read and tested on its own:

- `build_realtime_pdf_schema(client: MilvusClient, dim: int) -> CollectionSchema` — defines all fields and the BM25 Function described in §4.
- `build_realtime_pdf_index_params(client: MilvusClient) -> IndexParams` — defines both indexes described in §4.

### Modified: `backend/app/rag/vector_store.py::get_collection()`

Replace the inline schema/index construction with calls to the two new builder functions. No other change to this file — `add_chunks()`, `query_chunks()`, `delete_document()`, `list_documents()`, `indexed_file_hashes()` are untouched. In particular, `add_chunks()` does not need to know about `sparse_vector` at all; it keeps writing `{"text": ..., "embedding": ..., **chunk.metadata}`, and Milvus derives `sparse_vector` from `text` inside the same `insert()` call.

### Modified: `backend/app/rag/chunker.py::build_chunks_from_pages()`

Add a counter incremented once per chunk across **all pages of the document** (not reset per page, unlike `chunk_index` which resets at each page boundary). Written into each chunk's metadata as `chunk_seq` (1-indexed). This is scoped per-document, not per-collection: a new document upload starts its own `chunk_seq` at 1, exactly like `chunk_index` does today — the two are: `chunk_index` = position within this page, `chunk_seq` = position within this document.

### `backend/app/rag/types.py`

No change. `Chunk.metadata: dict[str, str | int]` already accepts an int `chunk_seq`.

## 6. Data flow (updated)

```
pages → build_chunks_from_pages()
          [chunk_index: resets per page | chunk_seq: monotonic per document]
      → embed_texts() [dense vector]
      → add_chunks() writes {text, embedding, chunk_seq, document_name, file_hash, page, chunk_index}
      → Milvus BM25 Function derives sparse_vector from text, in the same insert()
      → flush()
```

## 7. Testing

Extend `scripts/test_vector_store_milvus.py` (existing add→query→list→delete round-trip against a throwaway `test_realtime_pdf_collection`):

- After `add_chunks()`, query the raw client for `sparse_vector` and assert it's non-empty for inserted rows.
- Run a keyword-based search with `anns_field="sparse_vector"`, `metric_type="BM25"` and assert the chunk containing that literal keyword ranks first (verifies the Function + index actually work end-to-end, not just that the field exists).
- Add a 3-page fixture (currently the test only has 2 single-chunk pages) and assert `chunk_seq` is present on every chunk and strictly increasing 1..N across the whole set, while `chunk_index` resets to 1 at each page boundary — this is the one behavior distinguishing the two counters, so it's the one worth asserting explicitly.

No changes needed to `scripts/test_pdf_loader_chunker.py` — chunking behavior for `chunk_index`/text splitting is unaffected; it doesn't need to know about `chunk_seq`.

## 8. Explicitly out of scope

- Retrieval/query workflow (`retriever.py`, `reranker.py`, `Hybrid_retrieval.py`, `BM25_sparse_retrieval.py`) — not touched.
- Multi-language analyzer / per-document language detection — deferred, see §3.
- `offline_docs_store.py` / `OFFLINE_DOCS_COLLECTION_NAME` — separate collection, not part of the PDF upload workflow this spec covers.
- `docs/architecture.md` diagram/prose updates reflecting the new sparse_vector + chunk_seq steps — should happen once this lands, but as a follow-up doc update, not part of the implementation plan itself.
